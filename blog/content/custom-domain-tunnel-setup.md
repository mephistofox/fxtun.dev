## Зачем использовать кастомный домен для туннеля?

Кастомный домен превращает ваш [локальный туннель](/blog/what-is-tunneling/) в стабильную, профессиональную точку входа для разработки. Вместо `abc.fxtun.ru` ваш туннель отвечает по адресу `dev.yourcompany.com` — URL, который никогда не меняется, работает для всей команды и выглядит убедительно на демонстрациях клиентам. Настройка занимает около 5 минут.

Пробовали вписать случайный поддомен в OAuth redirect URI или в настройки вебхука Stripe? Стандартные поддомены `fxtun.ru` отлично подходят для личной разработки, но как только появляются интеграции со сторонними сервисами, командная работа или демо для клиентов — случайный поддомен начинает мешать. OAuth-провайдеры требуют стабильные redirect URI, вебхуки ломаются при смене URL, а клиенты ожидают нормальный адрес, а не что-то временное.

Вот что решает кастомный домен:

- **Стабильные URL для вебхуков** — сервисы вроде Stripe, GitHub и Telegram продолжают работать после перезапуска туннеля, потому что домен остаётся прежним. Не нужно обновлять настройки эндпоинтов. Подробнее — в статье [«Тестирование вебхуков через туннель»](/blog/webhook-testing-with-tunnel/).
- **Интеграция с OAuth и SSO** — провайдеры вроде Google, Auth0 и Okta позволяют зарегистрировать `https://dev.yourcompany.com/auth/callback` как постоянный redirect URI, что избавляет от необходимости обновлять его в процессе разработки.
- **Профессиональные демонстрации** — покажите клиенту `https://demo.yourcompany.com` вместо случайного поддомена. Это вызывает доверие и выглядит осознанно.
- **Единообразие в команде** — каждый разработчик в команде подключается к одному домену. QA может добавить URL в закладки. Ссылки в документации остаются актуальными.
- **Автоматический HTTPS** — fxTunnel выпускает валидный TLS-сертификат для вашего кастомного домена через Let's Encrypt. Никакого ручного управления сертификатами. Механика описана в статье [«HTTPS на localhost»](/blog/https-localhost-development/).

## Подготовка

Перед настройкой кастомного домена убедитесь, что у вас есть:

1. **Установленный fxTunnel CLI** — если ещё не установлен, выполните команду быстрой установки.
2. **Платный тариф fxTunnel** — кастомные домены доступны начиная с тарифа Base на [fxtun.ru](https://fxtun.ru).
3. **Зарегистрированный домен** — вам нужен доступ к DNS-настройкам принадлежащего вам домена (например, `example.com`).
4. **Аккаунт fxTunnel** — авторизуйтесь через `fxtunnel login` (или используйте `--token` для CI).

```bash
# Установка fxTunnel (Linux/macOS)
curl -fsSL https://fxtun.ru/install.sh | bash

# Проверка установки
fxtunnel version

# Авторизация в аккаунте
fxtunnel login
```

## Пошаговая настройка кастомного домена

Порядок такой: зарезервировать поддомен на `fxtun.ru`, привязать к нему кастомный домен, добавить у DNS-провайдера две записи (TXT для подтверждения владения и CNAME для трафика), подтвердить домен и запустить туннель на зарезервированном поддомене. TLS-сертификат сервер выпускает сам. Полная инструкция — в [документации по своим доменам](https://fxtun.ru/docs/custom-domains).

### Шаг 1. Резервирование поддомена и привязка домена

Трафик кастомного домена идёт на ваш зарезервированный поддомен, поэтому сначала резервируем его, а потом привязываем к нему домен (без резерва сервер откажет с ошибкой `target subdomain not owned by you`):

```bash
# Резервирование поддомена dev.fxtun.ru
fxtunnel domains add dev

# Привязка кастомного домена — --target указывает поддомен
fxtunnel domains custom add dev.example.com --target dev
```

Вывод последней команды:

```
Added: dev.example.com → dev [pending DNS verification]
Set up DNS records and run: fxtunnel domains custom verify dev.example.com
```

Домен можно добавить и в личном кабинете, в разделе «Домены». Там же, в карточке домена, лежит токен для TXT-записи.

### Шаг 2. DNS-записи

Войдите в панель управления DNS-провайдера (Cloudflare, Route 53, GoDaddy, Namecheap и др.) и добавьте две записи:

| Тип записи | Имя | Значение | TTL |
|---|---|---|---|
| TXT | `_fxtunnel-challenge.dev` | `fxtunnel-verify=<токен из карточки домена>` | 300 (5 мин) |
| CNAME | `dev` | `dev.fxtun.ru` | 300 (5 мин) |

TXT подтверждает, что домен ваш, CNAME направляет трафик `dev.example.com` на ваш поддомен `dev.fxtun.ru`. Многие провайдеры сами дописывают домен к имени записи, поэтому в поле «Имя» достаточно указать `dev` и `_fxtunnel-challenge.dev`.

**Корневой домен.** Для `example.com` вместо CNAME ставится A-запись на IP сервера, который указан в карточке домена. TXT-запись нужна так же: `_fxtunnel-challenge.example.com`.

#### Примеры настройки DNS по провайдерам

**Cloudflare:**

1. Перейдите в **DNS** > **Records** > **Add record**.
2. Type: `TXT`, Name: `_fxtunnel-challenge.dev`, Content: `fxtunnel-verify=<токен>`.
3. Type: `CNAME`, Name: `dev`, Target: `dev.fxtun.ru`.
4. Proxy status для CNAME: **DNS only** (серая иконка). Не включайте проксирование Cloudflare — fxTunnel самостоятельно управляет TLS, а с прокси проверка домена не пройдёт.

**AWS Route 53:**

1. Откройте вашу hosted zone.
2. Нажмите **Create record**: Record name `_fxtunnel-challenge.dev`, Record type `TXT`, Value `"fxtunnel-verify=<токен>"`.
3. Ещё одна запись: Record name `dev`, Record type `CNAME`, Value `dev.fxtun.ru`, TTL `300`.

**Namecheap:**

1. Перейдите в **Domain List** > **Advanced DNS**.
2. Добавьте записи: Type `TXT Record`, Host `_fxtunnel-challenge.dev`, Value `fxtunnel-verify=<токен>`; Type `CNAME`, Host `dev`, Value `dev.fxtun.ru`.

**GoDaddy:**

1. Перейдите в **My Products** > **DNS**.
2. Добавьте записи: Type `TXT`, Name `_fxtunnel-challenge.dev`, Value `fxtunnel-verify=<токен>`; Type `CNAME`, Name `dev`, Value `dev.fxtun.ru`.

### Шаг 3. Подтверждение домена

Когда записи разошлись по DNS, запустите проверку. Сервер сначала ищет TXT-запись, потом CNAME или A-запись:

```bash
fxtunnel domains custom verify dev.example.com
```

При успехе:

```
dev.example.com — verified! TLS certificate will be obtained automatically.
```

Если записи ещё не видны, команда напишет `dev.example.com — verification failed: …` с причиной. Подождите несколько минут и повторите: распространение DNS занимает от нескольких минут до нескольких часов. Проверять один домен можно не чаще раза в 30 секунд.

### Шаг 4. Запуск туннеля

После подтверждения запустите туннель на зарезервированном поддомене — `--domain` в fxTunnel задаёт именно поддомен, а не сам кастомный домен:

```bash
# Запуск туннеля на поддомене, к которому привязан dev.example.com
fxtunnel http 8080 --domain dev
```

Вывод (клиент печатает адрес поддомена; кастомный домен ведёт на него же):

```
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://dev.fxtun.ru
HTTPS: https://dev.fxtun.ru
Forwarding to localhost:8080
Inspector: http://127.0.0.1:4040
Ready to receive connections
```

Откройте `https://dev.example.com` в браузере. Вы увидите зелёный замок — TLS-сертификат валидный и доверенный. Весь трафик с `https://dev.example.com` теперь перенаправляется на ваш `localhost:8080`.

### Шаг 5. Проверка настройки

Выполните быструю проверку, чтобы убедиться, что всё работает:

```bash
# Проверка DNS-записей
dig TXT _fxtunnel-challenge.dev.example.com +short
# Ожидаемый результат: "fxtunnel-verify=…"
dig dev.example.com CNAME +short
# Ожидаемый результат: dev.fxtun.ru.

# Проверка HTTPS
curl -I https://dev.example.com
# Ожидаемый результат: HTTP/2 200

# Проверка деталей сертификата
openssl s_client -connect dev.example.com:443 -servername dev.example.com < /dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
# Ожидаемый результат:
# subject=CN = dev.example.com
# issuer=O = Let's Encrypt
# notBefore=...
# notAfter=...
```

## Управление TLS-сертификатами

fxTunnel управляет TLS-сертификатами для кастомных доменов автоматически. Сразу после подтверждения домена сервер запрашивает сертификат Let's Encrypt по протоколу ACME; если к первому HTTPS-запросу он ещё не готов, сервер получит его во время этого запроса. Сертификаты продлеваются автоматически до истечения срока действия. Вам никогда не нужно работать с файлами сертификатов вручную.

### Как это работает

1. TXT-запись `_fxtunnel-challenge.dev.example.com` подтверждает fxTunnel, что домен ваш; CNAME направляет `dev.example.com` на `dev.fxtun.ru`.
2. После `fxtunnel domains custom verify` сервер запрашивает сертификат для `dev.example.com` у Let's Encrypt по ACME.
3. Let's Encrypt выдаёт сертификат, и сервер его сохраняет.
4. Сертификат продлевается автоматически за 30 дней до окончания срока (сертификаты Let's Encrypt действительны 90 дней).

Не удаляйте TXT-запись после подтверждения: сервер перепроверяет её каждые 12 часов, и после трёх неудачных проверок подряд домен снова становится неподтверждённым.

Такой же подход используют CDN-провайдеры и [современные инструменты туннелирования](/blog/best-tunneling-tools-2026/). Разница в том, что вам ничего настраивать не нужно — всё работает само.

### Временные рамки выпуска сертификата

| Событие | Время |
|---|---|
| Распространение DNS-записей | от нескольких минут до нескольких часов |
| Первый выпуск сертификата | сразу после подтверждения домена |
| Продление сертификата | Автоматически, за 30 дней до истечения |
| Издатель | Let's Encrypt |

### Решение проблем с сертификатами

| Проблема | Причина | Решение |
|---|---|---|
| Сертификат не выпущен | Домен не подтверждён: TXT или CNAME не распространились | Проверьте записи с помощью `dig` и повторите `fxtunnel domains custom verify` |
| Предупреждение о невалидном сертификате | Включено проксирование Cloudflare | Отключите проксирование Cloudflare (используйте DNS-only режим) |
| Неправильный домен в сертификате | Конфликт с wildcard | Убедитесь, что нет конфликтующих DNS-записей |

## Кастомный домен vs. стандартный поддомен

Без флага `--domain` каждый запуск туннеля выдаёт новый случайный поддомен `fxtun.ru`. Чтобы получить постоянный адрес, нужно зарезервировать поддомен (`fxtunnel domains add myapp`, с тарифа Base) и запускать `fxtunnel http 8080 --domain myapp`. Кастомный домен добавляет брендирование, стабильность и удобство для команды поверх этого. Вот как они соотносятся.

| Характеристика | Стандартный поддомен (Free) | Кастомный домен (платный тариф) |
|---|---|---|
| **Формат URL** | `abc.fxtun.ru` | `dev.example.com` |
| **Сохраняется при перезапуске** | Нет — резерв поддомена доступен с тарифа Base | Да |
| **TLS-сертификат** | Автоматический | Автоматический (Let's Encrypt) |
| **Брендирование** | Брендинг fxTunnel | Ваш домен |
| **OAuth redirect URI** | Работает, но может потребовать обновления | Настроил один раз — работает всегда |
| **Webhook-эндпоинты** | Нестабильные без резерва (резерв — с тарифа Base) | Профессиональные, постоянные |
| **Демонстрации клиентам** | Выглядит временно | Выглядит как продакшен |
| **Использование в команде** | У каждого разработчика свой URL | Общий URL для всей команды |
| **Inspector + Replay** | Не включён | Включён |
| **Максимум туннелей** | 1 | 5–50 (в зависимости от тарифа) |

## Продвинутая настройка

### Несколько кастомных доменов

На тарифе Pro можно зарегистрировать до 5 кастомных доменов, на тарифе Business — до 50. Это полезно для микросервисных архитектур, где каждому сервису нужна собственная публичная точка входа.

```bash
# Резервирование поддоменов и привязка доменов (DNS и verify — как в шагах 2–3)
fxtunnel domains add api
fxtunnel domains add app
fxtunnel domains add admin
fxtunnel domains custom add api.example.com --target api
fxtunnel domains custom add app.example.com --target app
fxtunnel domains custom add admin.example.com --target admin

# Запуск туннелей — каждая команда работает, пока её не остановят,
# поэтому запускайте их в разных терминалах
fxtunnel http 3000 --domain api
fxtunnel http 3001 --domain app
fxtunnel http 3002 --domain admin
```

Каждый домен получает собственный TLS-сертификат, а каждый туннель перенаправляет трафик независимо.

### Использование кастомных доменов с Docker-контейнерами

Кастомные домены отлично работают с [Docker-контейнерами и туннелями](/blog/docker-tunnel-expose-containers/). Направьте туннель на порт контейнера вместо локального процесса:

```bash
# Запуск приложения в Docker
docker run -d -p 8080:80 my-web-app

# Открытие туннеля на поддомене, привязанном к кастомному домену
fxtunnel http 8080 --domain dev
```

Процесс идентичен — туннелю всё равно, откуда идёт трафик: из процесса на хосте или из контейнера.

### Домены для разных окружений

Распространённый паттерн — использование разных поддоменов для разных окружений:

```bash
# Разработка (dev.example.com -> поддомен dev)
fxtunnel http 3000 --domain dev

# Staging (staging.example.com -> поддомен staging)
fxtunnel http 3000 --domain staging

# QA (qa.example.com -> поддомен qa)
fxtunnel http 3000 --domain qa
```

Для каждого окружения нужны свой зарезервированный поддомен (`fxtunnel domains add ...`), свои TXT- и CNAME-записи и отдельная привязка домена (`fxtunnel domains custom add ... --target ...`). Это даёт командам чёткое разделение между окружениями, при этом всё остаётся доступным через стабильные URL.

## Командная работа с кастомными доменами

Именно в командной работе кастомные домены раскрываются по-настоящему. Единый брендированный URL упрощает взаимодействие, снижает расхождение конфигураций и избавляет QA, продакт-менеджеров и клиентов от вопроса «а какой сегодня URL?».

### Общее окружение разработки

Тимлид настраивает кастомный домен один раз. Любой авторизованный разработчик может затем запустить туннель на этом домене:

```bash
# Разработчик A запускает туннель утром
fxtunnel http 8080 --domain dev --token sk_fxtunnel_team_token

# Разработчик B подхватывает днём
# (Разработчик A сначала останавливает туннель)
fxtunnel http 8080 --domain dev --token sk_fxtunnel_team_token
```

QA добавляет `https://dev.example.com` в закладки и всегда видит последнюю версию приложения — вне зависимости от того, кто запустил туннель.

### Webhook-интеграции для команды

С кастомным доменом URL-адреса вебхуков остаются стабильными, независимо от того, кто из разработчиков запустил туннель. Настройте вебхук один раз в Stripe, GitHub или Telegram — и он продолжит работать, когда другой член команды возьмёт работу на себя:

```bash
# Webhook-эндпоинт Stripe (настраивается один раз)
# URL: https://dev.example.com/webhooks/stripe

# Любой разработчик может принимать вебхуки, запустив туннель
fxtunnel http 8080 --domain dev
```

Больше никаких «вебхук перестал работать, потому что URL изменился» — домен постоянный.

### CI/CD preview-окружения

Для стабильного адреса под каждую ветку CI-пайплайн может запускать туннель на поддомене, привязанном к ветке:

```bash
# В вашем CI-скрипте
BRANCH_SLUG=$(echo $CI_BRANCH | tr '/' '-' | tr '[:upper:]' '[:lower:]')
fxtunnel http 8080 --domain "${BRANCH_SLUG}"
```

Это создаёт preview-URL вроде `feature-login.fxtun.ru` для каждой ветки — доступный по HTTPS с автоматическим сертификатом. Подробнее о preview-окружениях в CI/CD — в статье [«CI/CD и превью-окружения с туннелями»](/blog/cicd-tunnel-preview-environments/).

## Тарифы fxTunnel для кастомных доменов

Кастомные домены недоступны на бесплатном тарифе; платные тарифы добавляют от 1 до 50 доменов в зависимости от уровня.

| Тариф | Кастомные домены | Туннели | Inspector + Replay |
|---|---|---|---|
| **Free** | Нет | 1 | Нет |
| **Base** | 1 | 5 | Да |
| **Pro** | 5 | 15 | Да |
| **Business** | 50 | 50 | Да |

Все тарифы включают:

- Поддержку HTTP и TCP туннелей (UDP — от тарифа Base)
- Возможность зарезервировать постоянный поддомен (`fxtunnel domains add`) — с тарифа Base
- [Шифрование TLS 1.2](/blog/tls-13-tunnel-security/)

Тариф Base добавляет первый кастомный домен и Inspector с Replay — веб-интерфейс для просмотра всех HTTP-запросов, проходящих через туннель, с возможностью повторить любой запрос одним кликом. Тарифы Pro и Business увеличивают лимиты по доменам и туннелям для растущих команд.

Зарегистрируйтесь на [fxtun.ru](https://fxtun.ru), чтобы начать. Клиент доступен на [GitHub](https://github.com/mephistofox/fxtun.dev), сервер можно развернуть у себя.

## Сравнение: кастомные домены у разных инструментов

Если кастомные домены для вас важны, вот как fxTunnel смотрится рядом с [ngrok и Cloudflare Tunnel](/blog/ngrok-vs-cloudflare-vs-fxtunnel/).

| Характеристика | fxTunnel | ngrok | Cloudflare Tunnel |
|---|---|---|---|
| **Кастомный домен** | Платный тариф | от $10/мес (платные тарифы) | Бесплатно (требуется DNS на Cloudflare) |
| **Управление сертификатами** | Автоматическое (Let's Encrypt) | Автоматическое | Автоматическое (Cloudflare CA) |
| **Wildcard-домены** | — | Только на платных тарифах | Да |
| **Сложность настройки** | TXT + CNAME + несколько команд CLI | CNAME + настройка в дашборде | Требуется миграция DNS на Cloudflare |
| **Inspector + Replay** | Платный тариф | от $10/мес | Нет встроенного инспектора |
| **Открытость кода** | Клиент открыт | Нет | Частично (cloudflared — OSS) |
| **Ограничения бесплатного тарифа** | 1 туннель, без UDP | Ограничения по трафику и запросам | Без ограничений трафика |

Поддержка протоколов шире, чем у Cloudflare Tunnel, а клиент открыт для аудита. И в отличие от Cloudflare Tunnel, вам не нужно переносить весь DNS на Cloudflare — достаточно добавить TXT- и CNAME-записи у любого провайдера.

## Безопасность

Кастомный домен, подключённый к туннелю, безопасен для использования в разработке — по умолчанию fxTunnel шифрует канал через [TLS 1.2](/blog/tls-13-tunnel-security/), автоматически выпускает сертификаты и изолирует туннели друг от друга. Но несколько привычек не помешают:

1. **Не открывайте продакшен-данные** — туннели предназначены для разработки и тестирования. Не подключайте туннель к продакшен-базе данных или сервису.
2. **Берегите токен** — туннель на вашем поддомене может запустить только ваш аккаунт; на рабочей машине вход через `fxtunnel login`, в CI — `--token` или `FXTUNNEL_TOKEN` из секретов. Не публикуйте токен в репозиториях.
3. **Ротируйте токены** — если член команды уходит, сгенерируйте новый токен и раздайте его оставшимся.
4. **Мониторьте через Inspector** — Inspector (доступен на платных тарифах) показывает все входящие запросы. Используйте его для обнаружения неожиданного трафика.
5. **Отключайте туннели, когда они не используются** — останавливайте туннель, когда заканчиваете разработку. DNS-записи домена останутся прежними, но туннеля за ними не будет — локальный сервис снаружи недоступен, пока вы снова не запустите туннель.

Токены создаются, отзываются и просматриваются в личном кабинете на fxtun.ru, а не командой CLI.

## Решение проблем

### Домен не резолвится

```bash
# Проверьте, правильно ли настроен CNAME
dig dev.example.com CNAME +short
# Ожидаемый результат: dev.fxtun.ru.

# Если пусто — DNS-запись ещё не распространилась
# Подождите 5-30 минут и попробуйте снова
```

### ERR_CONNECTION_REFUSED

Домен резолвится, но ничего не отвечает. Убедитесь, что туннель запущен:

```bash
fxtunnel http 8080 --domain dev
# Убедитесь, что ваш локальный сервер тоже запущен на порту 8080
```

### Ошибка SSL-сертификата

Если включено проксирование Cloudflare, вы увидите ошибки сертификата, потому что Cloudflare терминирует TLS раньше, чем fxTunnel сможет это сделать. Отключите проксирование (переключите в режим DNS-only в Cloudflare).

### Домен уже используется

Если вы видите «domain already registered», это значит, что кто-то другой уже зарегистрировал этот домен в fxTunnel. Убедитесь, что используете правильный аккаунт, или обратитесь в поддержку.

### Туннель запускается, но кастомный домен не работает

Проверьте статус верификации домена:

```bash
fxtunnel domains custom list
fxtunnel domains custom verify dev.example.com
```

Если статус «pending», сервер ещё не увидел TXT- или CNAME-запись. Перепроверьте DNS-настройки и подождите распространения.
