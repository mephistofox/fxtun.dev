У Битрикс24 два вида вебхуков. Входящий — это секретный адрес, по которому ваш код вызывает методы REST API. Для него достаточно `curl` с любого компьютера, туннель не нужен. Исходящий — наоборот: Битрикс24 сам отправляет POST-запрос на адрес вашего обработчика, когда в CRM что-то изменилось. Этот адрес должен быть публичным, `localhost` Битрикс24 не примет. Чтобы принять исходящий вебхук на своём компьютере, откройте туннель `fxtunnel http 8080` и укажите в Битрикс24 выданный HTTPS-адрес.

Ниже по шагам: обработчик на Python, туннель, настройка вебхука, проверка `application_token`, постоянный адрес и отладка без бесконечного редактирования сделок.

## Входящий и исходящий вебхук

Так их разделяет [документация Битрикс24](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html):

| | Входящий вебхук | Исходящий вебхук |
|---|---|---|
| Кто отправляет запрос | Ваш код → Битрикс24 | Битрикс24 → ваш обработчик |
| Что делает | Вызывает методы REST API по секретному URL | Сообщает о событии: сделка изменена, лид создан |
| Нужен ли публичный адрес у вас | Нет | Да |
| Где создать | Приложения > Разработчикам > Готовые сценарии > Другое > Входящий вебхук | Приложения > Разработчикам > Готовые сценарии > Другое > Исходящий вебхук |

Адрес входящего вебхука выглядит так:

```text
https://example.bitrix24.ru/rest/1/xxxxxxxx/profile.json
```

Здесь `example.bitrix24.ru` — ваш Битрикс24, `1` — идентификатор сотрудника, создавшего вебхук, `xxxxxxxx` — секретный код, `profile` — метод. Запросы идут с правами этого сотрудника и в рамках выбранных при создании scope. Секретный код даёт доступ к данным, поэтому URL вебхука не публикуют и не кладут в код фронтенда.

Исходящий вебхук устроен иначе. Документация прямо требует: URL обработчика должен быть публичным и доступным из внешней сети, нельзя указывать `localhost`, адреса локальной сети и обработчики с самоподписанным сертификатом. Вот тут и нужен туннель: он даёт публичный адрес `https://<поддомен>.fxtun.ru` с настоящим сертификатом.

## Что приходит в обработчик

Битрикс24 шлёт POST-запрос с телом `application/x-www-form-urlencoded`. Поля из примера документации для события изменения сделки `ONCRMDEALUPDATE`:

```text
event            = ONCRMDEALUPDATE
data[FIELDS][ID] = 662
ts               = 1724140800
auth[domain]            = example.bitrix24.ru
auth[member_id]         = xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
auth[application_token] = xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Полей сделки в событии нет, только её идентификатор. Документация советует взять ID из `data[FIELDS][ID]` и запросить полные данные методом `crm.item.get`. Как это сделать через входящий вебхук, покажем ниже.

## Шаг 1. Обработчик

Обработчик на стандартной библиотеке Python. Он принимает POST, сверяет `application_token` и печатает событие:

```python
# b24_hook.py
import hmac
import os
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs

TOKEN = os.environ["B24_APP_TOKEN"]


class Hook(BaseHTTPRequestHandler):
    def do_POST(self):
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        form = {k: v[0] for k, v in parse_qs(raw.decode(errors="replace")).items()}
        token = form.get("auth[application_token]", "")
        if not hmac.compare_digest(token.encode(), TOKEN.encode()):
            self.send_response(401)
            self.end_headers()
            return
        print(form.get("event"), form.get("data[FIELDS][ID]"), flush=True)
        self.send_response(200)
        self.end_headers()


HTTPServer(("127.0.0.1", 8080), Hook).serve_forever()
```

Токен обработчик берёт из переменной окружения `B24_APP_TOKEN`. Сам токен Битрикс24 покажет на шаге 3, поэтому запускать обработчик будем после настройки вебхука.

## Шаг 2. Туннель

Установите клиент и войдите (один раз):

```bash
curl -fsSL https://fxtun.ru/install.sh | sh
fxtunnel login
```

На Windows вместо первой строки выполните в PowerShell `irm https://fxtun.ru/install.ps1 | iex`.

Откройте туннель на порт обработчика. Имя поддомена задайте сразу, чтобы адрес в Битрикс24 не пришлось менять после каждого перезапуска:

```bash
fxtunnel http 8080 --domain crmhook
```

```console
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://crmhook.fxtun.ru
HTTPS: https://crmhook.fxtun.ru
Forwarding to localhost:8080
Inspector: http://127.0.0.1:4040
Ready to receive connections
```

Имя `crmhook` условное, выберите своё. Строка `Inspector:` появляется на тарифах с инспектором, на бесплатном её не будет. Окно с туннелем не закрывайте.

## Шаг 3. Исходящий вебхук в Битрикс24

По [документации](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html):

1. Откройте раздел **Приложения > Разработчикам**.
2. Перейдите на вкладку **Готовые сценарии > Другое > Исходящий вебхук**.
3. В URL обработчика укажите `https://crmhook.fxtun.ru/b24`.
4. Выберите событие, например изменение сделки (`ONCRMDEALUPDATE`).
5. Нажмите **Создать**.

При создании Битрикс24 покажет токен. Скопируйте его и запустите обработчик во втором окне терминала:

```bash
B24_APP_TOKEN=токен_из_настроек python3 b24_hook.py
```

На Windows в PowerShell: `$env:B24_APP_TOKEN="токен_из_настроек"; python b24_hook.py`.

Два ограничения из документации, о которые легко споткнуться: на демо-режиме исходящий вебхук недоступен, а в коробочной версии для него нужна активная лицензия.

## Шаг 4. Проверка

Откройте любую сделку в CRM и поменяйте в ней что-нибудь. В окне обработчика появится строка:

```console
ONCRMDEALUPDATE 662
```

Путь `/b24` из адреса доходит до обработчика как есть. Если на одном порту у вас живёт несколько обработчиков, их можно развести по путям.

## Проверка application_token

Адрес туннеля публичный. Узнав его, кто угодно может отправить на `/b24` запрос, похожий на событие Битрикс24. Документация даёт способ отличить настоящий: сравнить `auth[application_token]` в запросе с токеном из настроек исходящего вебхука. Не совпали — запросу доверять нельзя.

Обработчик выше так и делает: без правильного токена он отвечает `401` и событие не обрабатывает. Сравнение идёт через `hmac.compare_digest`, за постоянное время, а не обычным `==`. Токен храните как пароль: в переменной окружения или в хранилище секретов, но не в репозитории.

## Полные данные сделки через входящий вебхук

Событие сообщает только ID. Чтобы получить саму сделку, создайте входящий вебхук с правами на CRM (scope `crm`) и вызовите [`crm.item.get`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-get.html) с типом объекта `entityTypeId: 2` (сделка) и её `id`:

```bash
curl -X POST \
  -H "Content-Type: application/json" \
  -d '{"entityTypeId": 2, "id": 662}' \
  https://example.bitrix24.ru/rest/1/xxxxxxxx/crm.item.get
```

Этот запрос идёт от вас в Битрикс24, туннель ему не нужен. В обработчике его удобно делать после ответа `200`: сначала быстро подтвердить приём события, потом сходить за данными.

## Постоянный адрес

Без `--domain` каждый запуск `fxtunnel http 8080` даёт новый случайный поддомен, и исходящий вебхук продолжает слать события на вчерашний адрес. Флаг `--domain crmhook` решает это на любом тарифе, но с оговоркой: пока ваш туннель выключен, имя может занять кто-то другой.

Чтобы имя принадлежало только вам, зарезервируйте его:

```bash
fxtunnel domains add crmhook
```

```console
Reserved: crmhook → https://crmhook.fxtun.ru
```

Резерв доступен с тарифа Base. Для рабочей интеграции можно подключить и свой домен вида `b24.example.com`. Все варианты — в статье [«Постоянный адрес туннеля»](/blog/permanent-tunnel-address/).

## Отладка: повторить событие без правки сделки

Самое утомительное в работе с исходящими вебхуками — вызвать событие снова. Поправили обработчик и опять идёте в CRM менять сделку, и так двадцать раз за вечер.

Инспектор fxTunnel избавляет от этого круга. Откройте `http://127.0.0.1:4040` в браузере: там каждый запрос, который пришёл через туннель, с заголовками, телом в виде полей формы и ответом обработчика. Кнопка Replay («Повторить» в русском интерфейсе) отправляет сохранённый запрос в ваш локальный обработчик ещё раз, минуя сервер fxTunnel и сам Битрикс24 ([документация инспектора](https://fxtun.ru/docs/inspector)).

Работает это так:

1. Один раз меняете сделку в CRM, событие приходит и сохраняется в инспекторе.
2. Правите код обработчика и перезапускаете его.
3. Нажимаете Replay. Обработчик получает то же событие, с тем же `application_token`, и проходит проверку.

Инспектор слушает только `127.0.0.1` и не открывается с других компьютеров. Доступен он с тарифа Base. На бесплатном тарифе выручает печать запросов в самом обработчике, как в `b24_hook.py`. Подробнее о возможностях — в разборе [инспектора трафика](/blog/traffic-inspector-debug-requests/).

## Если событие не приходит

**Демо-режим или коробка без лицензии.** На демо-режиме исходящий вебхук недоступен, в коробочной версии ему нужна активная лицензия. Это ограничение Битрикс24, туннель тут ни при чём.

**Обработчик слушает другой порт.** Туннель открыт на 8080, а обработчик запущен на другом порту или не запущен вовсе. Запрос доходит до вашего компьютера, но не до кода. Сверьте число в `fxtunnel http 8080` с портом в `b24_hook.py`.

**Обработчик отвечает 401.** Токен в `B24_APP_TOKEN` не совпадает с токеном вебхука. Скопируйте его заново из настроек именно этого исходящего вебхука: у каждого вебхука свой.

**Адрес устарел.** Туннель перезапустили без `--domain`, и поддомен стал другим. Вебхук при этом шлёт события на старый адрес. Запускайте туннель с тем же именем или поправьте URL в настройках.

**Выбрано не то событие.** Вебхук на изменение сделки не сработает, когда вы создаёте лид. Проверьте список событий в настройках вебхука.
