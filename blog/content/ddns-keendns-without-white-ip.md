DDNS (динамический DNS) даёт постоянное имя вашему домашнему белому IP-адресу, который время от времени меняется. Если адрес серый, DDNS не поможет: имя будет указывать на общий адрес провайдера, за которым сидят сотни абонентов, и подключение до вас не дойдёт. У KeenDNS на роутерах Keenetic два рабочих режима. Прямой требует белого IP. Облачный работает и с серым, но пропускает только HTTP и HTTPS: веб-интерфейс роутера и веб-сервисы домашней сети на определённых портах. Для игр, RDP, SSH и всего остального без белого IP нужен туннель: клиент fxTunnel на домашнем компьютере даёт постоянный адрес вида `myhome.fxtun.ru` для сайта или порт на `fxtun.ru` для TCP и UDP.

## Что делает DDNS

Домашний провайдер обычно выдаёт адрес динамически: после переподключения или перезагрузки роутера он может смениться. Запоминать его и сообщать друзьям каждый раз неудобно. DDNS решает это так:

1. Вы регистрируете имя у сервиса DDNS, например `myhome.example-ddns.net`.
2. Роутер или программа на компьютере следит за внешним адресом и при смене сообщает новый сервису.
3. Сервис обновляет DNS-запись, и имя снова указывает на ваш текущий адрес.

Дальше всё как с белым IP: вы пробрасываете порт на роутере, и подключение по имени приходит на нужный компьютер. DDNS отвечает только за имя. Порты он не открывает, трафик через себя не пропускает, за NAT провайдера не проходит.

Отсюда главное ограничение. DDNS полезен, если адрес белый, но меняется. Если адрес серый, DNS-запись укажет на внешний адрес провайдерского NAT, общий для многих абонентов. Входящее подключение дойдёт до оборудования провайдера и там остановится: провайдер не знает, какому из абонентов его передать.

## Сначала проверьте, какой у вас адрес

Откройте веб-интерфейс роутера и найдите адрес подключения к интернету (WAN). Затем посмотрите свой внешний адрес на любом сайте проверки IP или командой:

```bash
curl -4 ifconfig.me
```

Если адреса совпадают, у вас белый IP, и DDNS с пробросом портов сработает. Если не совпадают или адрес роутера начинается с `10.`, `100.64`–`100.127`, `172.16`–`172.31`, `192.168.`, адрес серый. Подробно, с примерами, об этом в статье [«Серый IP: как узнать и что делать»](/blog/grey-ip-what-to-do/).

## KeenDNS: три режима

KeenDNS это бесплатный сервис доменных имён в роутерах Keenetic. Роутер получает имя вида `home.keenetic.pro` (домены `keenetic.pro`, `keenetic.name` и `keenetic.link`) и сам выпускает для него SSL-сертификат. В официальной справке описаны три режима работы ([Keenetic, KeenDNS service](https://support.keenetic.com/eu/titan/kn-1811/en/15882-dns-service.html)):

| Режим | Нужен белый IP | Что доступно |
|---|---|---|
| Прямой доступ (Direct access) | да | любые протоколы, если провайдер не ограничивает |
| Через облако (Cloud access) | нет | только HTTP и HTTPS на определённых портах |
| Авто | — | прямой доступ, пока адрес белый, облако, когда серый |

**Прямой доступ** работает как обычный DDNS: имя указывает на ваш белый адрес, а какие порты пробросить, решаете вы. С серым адресом роутер этот режим не включит и напишет, что прямой доступ с частным IP невозможен, и предложит облачный режим или купить белый IP у провайдера.

**Облачный режим** работает и с серым адресом. Роутер сам держит соединение с облачным сервером KeenDNS, а запросы из интернета приходят через этот сервер. Ограничения справка перечисляет прямо:

- только протоколы HTTP и HTTPS;
- HTTP на портах 80, 81, 280, 591, 777, 5080, 8080, 8090 и 65080, HTTPS на портах 443, 5083, 5443, 8083, 8443 и 65083;
- командная строка роутера через облако недоступна.

Кроме веб-интерфейса самого роутера через облако можно открыть веб-интерфейсы устройств домашней сети: сетевого накопителя, камеры, сервера. Для каждого создаётся имя четвёртого уровня, например `qnap.myrouter01.keenetic.pro` ([Keenetic, доступ к ресурсам домашней сети](https://support.keenetic.com/eu/titan/kn-1811/en/15884-remote-access-to-home-network-resources-with-dns.html)).

**Режим «Авто»** выбирает между ними сам. Пример из справки: основной провайдер даёт белый адрес, резервный канал через 3G/4G-модем серый. На основном канале имя работает напрямую, при переходе на резерв включается облако ([Keenetic, Automatic access type selection](https://support.keenetic.com/eu/titan/kn-1811/en/35112-automatic-access-type-selection-in-dns.html)).

С 2025 года компания, которая представляет Keenetic в странах ЕАЭС, выпускает роутеры этой линейки под своей маркой Netcraze ([блог Netcraze](https://blog.netcraze.ru/netcraze-the-beginning/)). Сервис там называется CrazeDNS, с доменами вроде `netcraze.pro`. Режимы, порты и ограничения в русской справке описаны так же ([Netcraze, сервис CrazeDNS](https://support.netcraze.ru/ultra/nc-1812/ru/15882-dns-service.html)).

## Чего облачный режим не откроет

В вопросах и ответах по KeenDNS есть прямой вопрос: можно ли через облако подключиться к домашним устройствам по FTP, RDP, RTSP или Telnet. Ответ: нет, только к веб-интерфейсам по HTTP и HTTPS ([Keenetic, KeenDNS FAQ](https://support.keenetic.com/eu/titan/kn-1811/en/36404-dns-frequently-asked-questions.html)). Там же про камеры: если камера отдаёт видео по HTTP, картинка через облако будет; если по RTSP или RTP, не будет. Для такого случая справка советует белый IP с прямым режимом или VPN.

Значит, с серым адресом KeenDNS не подойдёт для:

- игрового сервера (Minecraft, Valheim, Project Zomboid работают по TCP или UDP на своих портах);
- удалённого рабочего стола RDP;
- SSH к домашнему серверу;
- базы данных, SFTP, видеопотока RTSP;
- веб-сервиса на порту не из списка, если не настроить подмену порта на роутере.

А ещё облачный режим есть только у роутеров Keenetic и Netcraze. С роутером другой марки его нет вовсе.

## Туннель вместо DDNS

Туннель решает ту же задачу, что DDNS, только белый адрес ему не нужен. Клиент fxTunnel запускается на компьютере в домашней сети и сам подключается к серверу fxTunnel исходящим соединением, как браузер к сайту. Входящие подключения приходят на сервер fxTunnel и по этому соединению попадают к вам. Роутер, проброс портов и тип адреса значения не имеют.

Установите клиент и войдите, это делается один раз. На Linux и macOS:

```bash
curl -fsSL https://fxtun.ru/install.sh | sh
fxtunnel login
```

На Windows первая строка заменяется на `irm https://fxtun.ru/install.ps1 | iex` в PowerShell.

### Сайт или веб-сервис: постоянный поддомен

Для HTTP-сервиса аналогом имени DDNS служит поддомен на `fxtun.ru`:

```bash
fxtunnel http 8080 --domain myhome
```

```console
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://myhome.fxtun.ru
HTTPS: https://myhome.fxtun.ru
Forwarding to localhost:8080
Ready to receive connections
```

HTTPS работает сразу, сертификат выпускать не нужно. Порт сервиса может быть любым, списка разрешённых портов здесь нет.

Без `--domain` каждый запуск даёт новый случайный поддомен. С `--domain myhome` имя то же, но на бесплатном тарифе его может занять кто-то другой, пока ваш туннель выключен. Закрепить имя за собой можно с тарифа Base:

```bash
fxtunnel domains add myhome
```

Там же подключается свой домен вида `home.example.com`: зарезервированный поддомен, запись CNAME у регистратора и подтверждение. Порядок по шагам описан в статье [«Постоянный адрес туннеля»](/blog/permanent-tunnel-address/).

### Игры, RDP, SSH: TCP и UDP

Для всего, что не HTTP, туннель выдаёт порт на `fxtun.ru`:

```bash
fxtunnel tcp 22
```

```console
Connecting to fxtunnel server...
Tunnel established!
TCP: fxtun.ru:10022
Forwarding to localhost:22
Ready to receive connections
```

Номер `10022` здесь для примера: без флагов сервер выдаёт первый свободный порт из диапазона 10000–20000, и после перезапуска `fxtunnel` он будет другим. Чтобы адрес не менялся, попросите конкретный порт флагом `--remote-port 10022`. Резерва портов за аккаунтом нет: порт получает тот, кто занял его первым, и если он занят, клиент ответит `Failed to connect: server rejected tunnel: port 10022 is already in use`. Тогда выберите другой номер из диапазона.

UDP-туннели для игровых серверов открываются командой `fxtunnel udp` на тарифе Base и выше, порты для них из диапазона 20001–30000. Пример с двумя портами разобран в статье про [сервер Project Zomboid](/blog/project-zomboid-server-friends/).

### Устройство, на котором клиент не запустить

Камеру или сетевой накопитель можно открыть через клиент на соседнем компьютере. Команда принимает только номер порта на этом же компьютере, поэтому адрес другого устройства задаётся в конфигурационном файле полем `local_addr`:

```yaml
# fxtunnel.yaml
tunnels:
  - name: nas
    type: http
    local_addr: 192.168.1.50
    local_port: 80
    subdomain: mynas
```

Запускается это командой `fxtunnel --config fxtunnel.yaml`. Компьютер с клиентом должен быть включён: он передаёт запросы накопителю.

## Сравнение

| | DDNS | KeenDNS, облако | fxTunnel |
|---|---|---|---|
| Нужен белый IP | да | нет | нет |
| Нужен проброс портов | да | нет | нет |
| HTTP и HTTPS | да | да, на порты из списка | да, любой порт |
| TCP и UDP (игры, RDP, SSH) | да | нет | да, TCP с бесплатного тарифа, UDP с Base |
| Постоянное имя | да | да | поддомен с резервом на Base, порт через `--remote-port` |
| Где работает | роутер или ПК | роутер Keenetic или Netcraze | компьютер с клиентом |

Если адрес белый и роутер умеет DDNS или KeenDNS в прямом режиме, туннель не нужен: пробросьте порт, и всё. Если вам нужен только веб-интерфейс роутера или камеры по HTTP, а роутер Keenetic, хватит облачного режима. Туннель нужен, когда адрес серый, а сервис не веб: игра, RDP, SSH, база данных.

## Защитите то, что открыли

Адрес туннеля публичный, как и имя DDNS. Кто его узнал, тот и стучится. У fxTunnel два встроенных ограничения:

- `--auth user:password` — пароль на HTTP-туннель (только для HTTP);
- `--allow-ip 203.0.113.10` — пускать только перечисленные адреса и подсети, работает у HTTP, TCP и UDP.

```bash
fxtunnel http 8080 --domain myhome --auth family:LongPass-2026x --allow-ip 203.0.113.0/24
```

Для RDP и SSH, у которых пароля на стороне туннеля нет, главная мера — `--allow-ip`, плюс вход по ключу для SSH и NLA для RDP. Подробно — в статье [«Пароль и список IP для туннеля»](/blog/tunnel-password-and-ip-allowlist/).
