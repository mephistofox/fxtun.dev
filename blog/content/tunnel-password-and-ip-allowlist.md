Адрес туннеля публичный: кто его узнал, тот и открывает. У fxTunnel для этого два встроенных замка. `--auth user:password` включает HTTP Basic Auth и работает только у HTTP-туннелей. `--allow-ip` пускает только перечисленные адреса и подсети и работает у HTTP-, TCP- и UDP-туннелей. Оба флага доступны на любом тарифе, включая бесплатный. Проверку делает сервер fxTunnel: чужой запрос отсекается ещё до того, как дойдёт до вашего компьютера.

## Что проверяет сервер и в каком порядке

Для HTTP-туннеля сервер fxTunnel проверяет запрос по шагам:

1. **Список IP.** Адреса нет в `--allow-ip` — ответ `403 Forbidden`, дальше запрос не идёт.
2. **Лимит частоты.** Больше 360 запросов в минуту с одного IP или 3600 на туннель — ответ `429 Too Many Requests` ([лимиты](https://fxtun.ru/docs/limits)).
3. **Пароль.** Нет логина и пароля или они неверные — ответ `401 Unauthorized`.
4. Только после этого запрос уходит к клиенту на ваш компьютер.

У TCP-туннеля пароля нет, а соединение с адреса не из списка сервер сразу закрывает. У UDP-туннеля пакет с чужого адреса отбрасывается ([документация TCP](https://fxtun.ru/docs/tcp), [UDP](https://fxtun.ru/docs/udp)).

## Установка

Если клиента ещё нет:

```bash
curl -fsSL https://fxtun.ru/install.sh | sh
fxtunnel login
```

На Windows первая строка заменяется на `irm https://fxtun.ru/install.ps1 | iex` в PowerShell.

## Пароль на HTTP-туннель: --auth

```bash
fxtunnel http 3000 --auth team:MySecurePass123
```

```console
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://lemon.fxtun.ru
HTTPS: https://lemon.fxtun.ru
Forwarding to localhost:3000
Basic Auth: enabled
Ready to receive connections
```

Строка `Basic Auth: enabled` значит, что сервер принял пароль для этого туннеля. Браузер при первом заходе покажет стандартное окно входа, а после ввода запомнит логин до закрытия.

Правила для значения `user:password`:

- **Пароль не короче 8 символов, логин не пустой.** Иначе клиент не запустится: `invalid --auth: password must be at least 8 characters`.
- **Логин отделяется первым двоеточием.** В логине двоеточия быть не может, в пароле может.
- **Логин, двоеточие и пароль вместе — до 72 байт.** Это ограничение bcrypt: длиннее клиент не примет и напишет `failed to hash auth credentials`. Буква кириллицы в UTF-8 занимает 2 байта, так что русский пароль упрётся в предел примерно вдвое раньше латинского.

Сам пароль на сервер не уходит: клиент отправляет его bcrypt-хеш, и сервер сверяет с ним каждый запрос ([документация](https://fxtun.ru/docs/http)).

### Проверка через curl

Без пароля:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://lemon.fxtun.ru
```

```console
401
```

С паролем:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -u team:MySecurePass123 https://lemon.fxtun.ru
```

```console
200
```

Код `200` значит, что пароль принят. Если ваше приложение отвечает HTML, то при запросе через curl вместо него придёт страница-предупреждение fxTunnel, которую поддомены `fxtun.ru` показывают браузерам при первом заходе. Чтобы увидеть ответ самого приложения, добавьте заголовок `-H 'X-FxTunnel-Skip-Warning: 1'`.

### Где пароль мешает

**Приложение с собственной авторизацией через заголовок.** Basic Auth передаёт логин и пароль в заголовке `Authorization`, а он в запросе один. API с токеном `Authorization: Bearer …`, WebDAV, приложения, которые сами спрашивают пароль в этом же заголовке, с `--auth` не уживутся. Их защищайте списком IP.

**Вебхуки.** Сервис, который присылает вам события, обычно не умеет добавлять логин и пароль, и получит `401`. Для вебхуков подходит `--allow-ip` с адресами отправителя, если сервис их публикует, и проверка подписи в самом обработчике.

**Заголовок доходит до приложения.** Запрос с паролем передаётся локальному сервису целиком, вместе с `Authorization`. Не пишите этот заголовок в логи приложения.

**История команд.** Пароль из `--auth` остаётся в истории оболочки и виден в списке процессов. Если это важно, храните его в конфигурационном файле (об этом ниже) или используйте пресет `--preset openclaw`: он придумывает случайный пароль из 16 символов при каждом запуске и печатает его перед подключением.

## Список адресов: --allow-ip

```bash
fxtunnel tcp 5432 --allow-ip 203.0.113.10 --allow-ip 198.51.100.0/24
```

```console
Connecting to fxtunnel server...
Tunnel established!
TCP: fxtun.ru:15432
Forwarding to localhost:5432
IP Allowlist: 2 entries
Ready to receive connections
```

Строка `IP Allowlist: 2 entries` показывает, сколько записей в списке; при одной записи клиент напишет `1 entry`. Что можно передать:

- одиночный адрес IPv4 или IPv6: `203.0.113.10`;
- подсеть в записи CIDR: `198.51.100.0/24`;
- несколько значений: флаг повторяется или значения идут через запятую, `--allow-ip 203.0.113.10,198.51.100.0/24`.

Ошибку в адресе клиент поймает до подключения: `invalid --allow-ip address "203.0.113"`.

Свой внешний адрес узнайте командой `curl -4 ifconfig.me` или на любом сайте проверки IP. Нужен именно IPv4: посетители приходят на `fxtun.ru` по IPv4.

Сервер сверяет список с настоящим адресом, с которого пришло подключение. Подставить разрешённый адрес через заголовок `X-Forwarded-For` не выйдет: сервер доверяет такому заголовку только от своего прокси.

### Где список IP подводит

**Меняющийся домашний адрес.** У многих домашних провайдеров внешний IP время от времени меняется. Утром всё работало, вечером `403`. Узнайте новый адрес и перезапустите туннель, или разрешите подсеть провайдера, понимая, что вместе с вами в неё входят его другие абоненты.

**Мобильный интернет и общий NAT.** Под одним внешним адресом оператора сидят сотни абонентов. Разрешили такой адрес — пустили их всех. Для мобильного доступа список IP почти бесполезен, лучше пароль.

**Лучший случай** — статический адрес офиса или сервера: он не меняется, и за ним только свои.

## Пароль и список вместе

Флаги сочетаются. Для админки или демо заказчику так надёжнее всего: чужой адрес получит `403` раньше, чем увидит окно пароля.

```bash
fxtunnel http 3000 --auth team:MySecurePass123 --allow-ip 203.0.113.0/24
```

```console
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://lemon.fxtun.ru
HTTPS: https://lemon.fxtun.ru
Forwarding to localhost:3000
Basic Auth: enabled
IP Allowlist: 1 entry
Ready to receive connections
```

## В конфигурационном файле

Флагам соответствуют поля `basic_auth` и `allow_ips` в `fxtunnel.yaml` ([документация](https://fxtun.ru/docs/config)):

```yaml
# fxtunnel.yaml
tunnels:
  - name: admin
    type: http
    local_port: 3000
    subdomain: myadmin
    basic_auth: "team:MySecurePass123"
    allow_ips:
      - 203.0.113.0/24
```

Запуск — `fxtunnel` из папки с файлом: клиент работает в переднем плане и печатает тот же вывод, что выше, со строками `Basic Auth: enabled` и `IP Allowlist: 1 entry`. Команда `fxtunnel up` поднимает те же туннели в фоне, но печатает только `Daemon started (PID …)`, адреса туннелей и `Uptime`, без строк о пароле и списке ([подробнее](/blog/fxtunnel-up-config/)). Проверить защиту в этом режиме можно через `curl`, как описано выше.

Что учесть:

- **`basic_auth` работает только у `type: http`.** У TCP- и UDP-туннелей поле ни на что не влияет, и строки `Basic Auth: enabled` у них в выводе не будет.
- **Пароль в файле лежит открытым текстом.** На сервер клиент отправит хеш, но на диске пароль виден. Закройте файл от чужих глаз: `chmod 600 fxtunnel.yaml`, и не кладите его в репозиторий.
- **Адреса из файла проверяет сервер.** Ошибка в `allow_ips` всплывёт не при запуске клиента, а ответом сервера: `server rejected tunnel: invalid allow_ips: …`.
- **На бесплатном тарифе работает один туннель.** Файл с двумя туннелями поднимет только первый. Несколько защищённых туннелей одновременно — с тарифа Base.

## TCP и UDP: пароля нет, что вместо него

У TCP- и UDP-туннелей нет `--auth`: сервер fxTunnel не знает протокола вашего сервиса и не может спросить пароль. Поэтому для SSH, баз данных, удалённого рабочего стола и игровых серверов защита складывается из нескольких слоёв:

- **`--allow-ip`** — главная мера со стороны туннеля;
- **пароль или ключ самого сервиса**: вход по ключу для SSH, отдельный пользователь с длинным паролем для базы, NLA для RDP;
- **ограничения в самом сервисе**: белый список игроков, права пользователя в базе;
- **временный туннель**: `--max-lifetime 3h` закроет его через три часа, `--auto-close 30m` — после получаса без трафика.

Проверить список у TCP-туннеля проще всего настоящим клиентом с чужого адреса, например с телефона через мобильный интернет. TCP-соединение установится и тут сразу закроется: ssh сообщит, что соединение закрыто удалённой стороной, `psql` — что сервер неожиданно закрыл соединение. Утилиты вроде `nc -z`, которые проверяют только факт соединения, покажут успех и введут в заблуждение.

## Чего эти флаги не заменяют

Basic Auth — простой замок. Запрета входа после неудачных попыток у него нет, подбор пароля сдерживает только общий лимит в 360 запросов в минуту с одного IP. Поэтому пароль нужен длинный и не словарный.

Оба флага защищают вход в туннель, но не само приложение. Если через туннель открыта админка с уязвимостью, пустят к ней только своих, но свои доберутся до уязвимости так же легко. Обновления, права доступа и собственный вход приложения остаются на вас.
