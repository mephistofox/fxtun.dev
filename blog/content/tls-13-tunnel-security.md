## Зачем туннелю шифрование

Когда вы создаёте туннель, ваш трафик проходит через relay-сервер. Каждый HTTP-запрос, каждый заголовок авторизации, каждое тело ответа — всё через этот узел. Если канал между клиентом и relay не зашифрован, любой на маршруте может прочитать и подменить данные: провайдер, оператор Wi-Fi, злоумышленник на промежуточном хопе. Подробнее о том, как устроены туннели — в статье [«Что такое туннелирование»](/blog/what-is-tunneling/).

Это не теоретическая угроза. При [тестировании вебхуков](/blog/webhook-testing-with-tunnel/) через туннель проходят подписи запросов (webhook secrets), токены API, данные пользователей. При демонстрации проекта клиенту — сессионные куки и учётные данные. Без шифрования все эти данные передаются в открытом виде.

TLS (Transport Layer Security) решает эту проблему, шифруя трафик между клиентом туннеля и сервером.

## TLS 1.2: что защищает канал

По умолчанию канал между клиентом fxTunnel и сервером идёт через TLS 1.2. Это зрелая версия протокола с известной моделью безопасности:

- **Обмен ключами по ECDHE** (Elliptic-curve Diffie-Hellman) — для каждого соединения генерируется новый сеансовый ключ. Даже если долгосрочный ключ сервера когда-нибудь утечёт, расшифровать ранее записанный трафик по нему нельзя (forward secrecy).
- **AEAD-шифры** (например, AES-GCM) — шифрование и проверка целостности данных выполняются одной операцией, поэтому подмена содержимого пакета обнаруживается на принимающей стороне.
- **Проверка сертификата сервера** — клиент сверяет цепочку доверия и имя хоста при подключении. Эта проверка включена по умолчанию: клиент не примет произвольный сертификат.

## Как устроено шифрование в fxTunnel

Стандартный адрес SaaS-клиента — `tunnel.fxtun.ru:443`, канал защищён TLS 1.2, сертификат сервера проверяется по умолчанию.

Для посетителей поддоменов `*.fxtun.ru` TLS тоже завершается на TLS 1.2 — на nginx перед сервером туннелей. Для собственных доменов пользователей сервер поднимает отдельный HTTPS-слушатель с сертификатами, которые выпускаются автоматически через ACME (Let's Encrypt), и выбирает нужный сертификат по SNI. Подробнее — в статье [«Настройка своего домена для туннеля»](/blog/custom-domain-tunnel-setup/).

Есть и запасной адрес — `fxtun.ru:4443`, на который клиент переключается, если основной порт 443 недоступен. Это честно **незашифрованный канал**: TLS там нет. Если вы полагаетесь на этот адрес, учитывайте, что трафик между клиентом и сервером на нём идёт открытым текстом.

При self-hosted развёртывании сервер по умолчанию слушает управляющий порт 4443 открытым текстом — TLS для управляющего канала включается отдельной настройкой (`tls.enabled`, `control_tls.enabled`).

### Конфигурация TLS в fxTunnel

```go
// Упрощённый пример конфигурации TLS в fxTunnel
tlsConfig := &tls.Config{
    MinVersion: tls.VersionTLS12,
    MaxVersion: tls.VersionTLS12,
    // Сертификат загружается автоматически
    GetCertificate: certManager.GetCertificate,
}
```

### Автоматическое управление сертификатами

Для SaaS-сервиса на [fxtun.ru](https://fxtun.ru) fxTunnel использует автоматическое получение и обновление сертификатов. При self-hosted развёртывании можно указать собственный сертификат или использовать автоматическое получение через ACME (Let's Encrypt).

```bash
# SaaS — TLS работает автоматически
fxtunnel http 8080
# → https://abc123.fxtun.ru
```

При self-hosted развёртывании TLS и сертификаты настраиваются не флагами командной строки, а в конфиге сервера (`server.yaml`) перед запуском `fxtunnel-server`.

### Почему Go crypto/tls — надёжный выбор

Сервер fxTunnel использует стандартную библиотеку Go `crypto/tls`, клиент — открытую библиотеку utls, построенную на её основе. `crypto/tls` не является обёрткой над OpenSSL, а написана на Go, что исключает целые классы уязвимостей (переполнение буфера, use-after-free). Исходный код открыт и обновляется вместе с релизами Go.

## Где защита заканчивается

Сквозного шифрования до localhost нет. На сервере fxTunnel трафик расшифровывается — а дальше, между сервером и вашим локальным сервисом, идёт то, что говорит сам сервис. Обычно это открытый HTTP на localhost. Если вам нужно шифрование и на этом участке — поднимайте локальный сервис с собственным TLS.

## Риски незашифрованных туннелей

Что будет, если пропустить TLS? Представьте, что вы отправляете конфиденциальные документы открытой почтой, где каждый почтальон может заглянуть внутрь. Вот конкретные угрозы.

### Перехват данных (sniffing)

Без TLS любой узел между вашим компьютером и relay-сервером видит трафик в открытом виде. В корпоративной сети — администратор. В кафе — любой в той же Wi-Fi сети. На хостинге — оператор дата-центра.

### Модификация трафика (MITM)

Без аутентификации сервера через сертификат злоумышленник может подменить relay-сервер, перехватывать запросы и подставлять свои ответы. Классическая man-in-the-middle атака.

### Кража токенов и учётных данных

API-ключи, сессионные куки, заголовки `Authorization: Bearer` — всё это проходит через туннель. Без шифрования эти данные доступны каждому, кто имеет доступ к сетевому трафику.

### Injection-атаки

Злоумышленник может модифицировать ответы сервера, внедряя вредоносный JavaScript в HTML-страницы или изменяя JSON-ответы API. Клиент на другом конце туннеля не заметит подмены.

Вывод прост: **незашифрованный туннель — это не туннель, а открытая труба.** Если инструмент не включает TLS по умолчанию, стоит дважды подумать, прежде чем доверять ему свой трафик. У fxTunnel TLS включён по умолчанию; исключение — запасной адрес `fxtun.ru:4443` без TLS (см. выше).

## Открытость и аудит

Шифрование надёжно ровно настолько, насколько надёжна его реализация. Клиент fxTunnel открыт на [GitHub](https://github.com/mephistofox/fxtun.dev) — можно проверить, как настроена конфигурация TLS и как клиент проверяет сертификат сервера. Сервер можно развернуть у себя, если нужен полный контроль над каналом. Вот что это даёт по сравнению с [закрытыми аналогами](/blog/ngrok-vs-cloudflare-vs-fxtunnel/).

### Аудируемая реализация клиента

Код клиента открыт. Любой разработчик может проверить, что TLS действительно используется, что минимальная версия установлена корректно и что сертификат сервера проверяется. С закрытым инструментом вы вынуждены верить документации.

### Прозрачность на стороне клиента

Relay-сервер видит метаданные соединений (IP-адреса, тайминги). В открытом клиенте можно убедиться, какие данные он отправляет и как настроена проверка сертификата. Если нужна прозрачность и на стороне сервера — разверните его у себя.

### Зависимости под контролем

Клиент fxTunnel построен на стандартной библиотеке Go и открытых библиотеках — например, yamux для мультиплексирования и utls для TLS. Каждая из них открыта и аудируема. Нет скрытых бинарных модулей или обфусцированного кода.

### Сообщество как фактор безопасности

Ошибки в открытом коде обнаруживаются быстрее — его может прочитать кто угодно. Для клиента, через который проходит чувствительный трафик, это важное свойство.

## Лучшие практики безопасного туннелирования

TLS берёт на себя криптографию, но всё остальное — на вас. Вот правила, которым стоит следовать.

### 1. Используйте только инструменты с TLS по умолчанию

Не доверяйте инструментам, которые предлагают «опциональное» шифрование. fxTunnel по умолчанию шифрует канал до сервера — настраивать ничего не нужно. Исключение — запасной адрес `fxtun.ru:4443` без TLS, на который клиент переходит, если порт 443 недоступен.

### 2. Проверяйте версию TLS

Убедитесь, что ваш инструмент использует не ниже TLS 1.2. Проверить можно через браузер (значок замка → сведения о сертификате) или через командную строку:

```bash
# Проверка версии TLS для вашего туннеля
openssl s_client -connect your-tunnel.fxtun.ru:443 2>/dev/null | grep "Protocol"
# → Protocol  : TLSv1.2
```

### 3. Не оставляйте туннель запущенным без необходимости

Каждый активный туннель — это точка входа в вашу систему. Закончили тестирование — остановите клиент (`Ctrl+C`).

### 4. Используйте тестовые данные

При работе через туннель используйте тестовую базу данных, тестовые API-ключи и тестовые учётные записи. Не пробрасывайте продакшен-сервисы через туннель.

### 5. Проверяйте подписи вебхуков

Даже с TLS рекомендуется проверять подписи входящих вебхуков на стороне сервера. Это дополнительный уровень защиты от подмены запросов.

### 6. Выбирайте инструменты с открытым клиентом

Для [туннелирования](/blog/what-is-tunneling/) предпочитайте решения, где можно проверить хотя бы клиентскую часть реализации безопасности. Клиент fxTunnel открыт и поддерживает HTTP, [TCP и UDP](/blog/tcp-udp-tunneling-explained/).

### 7. Обновляйте клиент

Исправления безопасности приходят с новыми версиями клиента. Используйте актуальную версию (`fxtunnel update`).
