Туннель, открытый «на пять минут», легко забыть на неделю, и всё это время адрес публичен. У fxTunnel для этого два флага. `--auto-close 30m` закрывает туннель, если через него 30 минут не шёл трафик. `--max-lifetime 8h` закрывает его через 8 часов после подключения, что бы ни происходило. Флаги работают у HTTP-, TCP- и UDP-туннелей на любом тарифе, включая бесплатный (UDP-туннели — с тарифа Base). Когда закрывается последний туннель, клиент печатает `All tunnels closed, exiting` и завершает работу. Ниже разберём, как считаются таймеры, что с ними бывает при обрыве сети и как ими пользоваться для демо, доступа к RDP на час и CI.

## Два таймера

| Флаг | Когда закрывает | Допустимо |
|---|---|---|
| `--auto-close` | через заданное время без трафика | от `1m` до `24h` |
| `--max-lifetime` | через заданное время после подключения, независимо от активности | от `1m` до `7d` |

Значение пишется числом с единицей: `m` — минуты, `h` — часы, `d` — дни. Примеры: `45m`, `1h30m`, `8h`, `2d`. Флаги можно ставить вместе, тогда туннель закроется по тому, что наступит раньше.

Значение вне пределов клиент не примет ещё до подключения:

```console
Error: auto-close minimum is 1m, got 30s
```

Для `--max-lifetime` сообщение такое же, с верхним пределом `7d`.

## Что видно при запуске

Установите клиент и войдите, если ещё не сделали этого:

```bash
curl -fsSL https://fxtun.ru/install.sh | sh
fxtunnel login
```

На Windows первая строка заменяется на `irm https://fxtun.ru/install.ps1 | iex` в PowerShell.

Туннель с обоими таймерами:

```bash
fxtunnel http 3000 --auto-close 30m --max-lifetime 8h
```

```console
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://lemon.fxtun.ru
HTTPS: https://lemon.fxtun.ru
Forwarding to localhost:3000
Auto-close: 30m (idle timeout)
Max lifetime: 8h
Ready to receive connections
```

Строки `Auto-close:` и `Max lifetime:` подтверждают, что сервер принял значения. На тарифах с инспектором перед последней строкой будет ещё `Inspector: http://127.0.0.1:4040`.

## Что происходит, когда срок вышел

Таймеры считает клиент на вашем компьютере. Когда срок выходит, клиент:

1. отправляет серверу fxTunnel команду закрыть туннель, и адрес перестаёт принимать подключения;
2. удаляет туннель из своего списка, так что при переподключении к серверу он заново не откроется;
3. если это был последний туннель, печатает `All tunnels closed, exiting` и завершается с кодом 0.

Причину закрытия клиент пишет в журнал на уровне info, а по умолчанию журнал показывает только предупреждения и ошибки. Чтобы видеть строку `tunnel auto-closed` с причиной, запустите клиент с `--log-level info`.

Если туннелей несколько (из конфигурационного файла), закрывается только тот, у которого вышел срок. Остальные работают, а клиент завершится, когда закроется последний.

Ваш локальный сервис таймер не трогает. Сайт на `localhost:3000` или RDP продолжают работать в домашней сети, закрывается только дорога к ним из интернета.

### Что считается активностью

Для `--auto-close` активностью считается любой трафик через туннель: новое подключение или данные внутри уже открытого. Клиент смотрит на счётчики раз в секунду. Долгая загрузка файла или поток событий (SSE) держат туннель открытым, пока по ним идут данные. Туннель закроется, когда данные перестанут идти на весь заданный срок.

### Обрыв сети сбрасывает таймеры

Если связь с сервером оборвалась, клиент переподключается сам и заново открывает туннели. Таймеры при этом начинают отсчёт заново ([справочник CLI](https://fxtun.ru/docs/cli)). Туннель с `--max-lifetime 8h`, который переподключился через 7 часов, проживёт ещё до 8 часов.

Для демо это не важно. Если же нужен жёсткий предел для доступа к рабочему компьютеру, ограничьте сам процесс средствами системы. На Linux это делает утилита `timeout`:

```bash
timeout 1h fxtunnel tcp 3389 --max-lifetime 1h
```

Через час система остановит клиент, даже если отсчёт `--max-lifetime` начинался заново. На Windows встроенного аналога нет (тамошняя команда `timeout` только ждёт), поэтому полагайтесь на `--max-lifetime` и останавливайте клиент сами, `Ctrl+C`.

Если в фоне работает `fxtunnel up`, `timeout` ничего не ограничит: команда передаст туннель фоновому процессу и сразу завершится (подробнее ниже, в разделе о конфигурационном файле).

## Сценарий 1. Показать демо заказчику

Заказчик смотрит сайт днём, вечером адрес не нужен. Пароль закрывает демо от случайных посетителей, `--auto-close` закроет туннель, если о нём забыли, а `--max-lifetime` не даст ему дожить до следующего дня.

```bash
fxtunnel http 3000 --auth client:DemoPass-2026x --auto-close 1h --max-lifetime 10h
```

```console
Connecting to fxtunnel server...
Tunnel established!
HTTP:  http://lemon.fxtun.ru
HTTPS: https://lemon.fxtun.ru
Forwarding to localhost:3000
Basic Auth: enabled
Auto-close: 1h (idle timeout)
Max lifetime: 10h
Ready to receive connections
```

`--auth` есть только у HTTP-туннелей. Пароль нужен от 8 символов. Клиент хэширует bcrypt строку `логин:пароль` целиком, вместе с двоеточием, а bcrypt берёт не больше 72 байт, так что на логин и пароль остаётся 71 байт. Буква кириллицы занимает 2 байта. Подробно про пароль и список адресов написано в статье [«Пароль и список IP для туннеля»](/blog/tunnel-password-and-ip-allowlist/). Как собрать демо целиком — в статье [«Как показать локальный проект клиенту без деплоя»](/blog/demo-localhost-without-deploy/).

## Сценарий 2. Доступ к RDP на час

Коллеге нужно зайти на ваш компьютер, или вам на домашний из поездки. Открытый в интернет порт RDP опасен: его находят сканеры и начинают подбирать пароли. Поэтому туннель должен пускать только нужный адрес и жить недолго.

Сначала узнайте внешний адрес того, кто будет подключаться: пусть он откроет любой сайт проверки IP или выполнит `curl -4 ifconfig.me`. Затем на компьютере, к которому подключаются:

```bash
fxtunnel tcp 3389 --allow-ip 203.0.113.10 --max-lifetime 1h
```

```console
Connecting to fxtunnel server...
Tunnel established!
TCP: fxtun.ru:10417
Forwarding to localhost:3389
IP Allowlist: 1 entry
Max lifetime: 1h
Ready to receive connections
```

Номер порта `10417` для примера: без `--remote-port` сервер выдаёт первый свободный из диапазона 10000–20000. Коллега подключается клиентом удалённого рабочего стола к адресу `fxtun.ru:10417`. С любого другого адреса сервер fxTunnel закроет соединение сразу, а через час туннель закроется целиком.

TCP-туннель работает и на бесплатном тарифе. Пароля на стороне туннеля у TCP нет, `--auth` здесь не работает, поэтому остальную защиту даёт сам Windows:

- длинный пароль у учётной записи, через которую входят;
- NLA (проверка подлинности на уровне сети) включена в настройках удалённого рабочего стола;
- удалённый вход разрешён только нужным пользователям.

`--auto-close` для RDP полезен как добавка: `--auto-close 15m` закроет туннель, если через него четверть часа не шло данных.

## Сценарий 3. Туннель в CI

В пайплайне туннель нужен на время тестов: внешний сервис должен достучаться до приложения, поднятого в задаче. Если шаг с остановкой туннеля не выполнится, клиент может висеть до тайм-аута всей задачи. `--max-lifetime` ставит ему свой предел.

Токен API создаётся в личном кабинете и передаётся через переменную окружения `FXTUNNEL_TOKEN`, секретом CI. Клиент пишет строки с адресом в stdout, поэтому вывод перенаправляем в файл целиком:

```bash
fxtunnel http 3000 --max-lifetime 30m > tunnel.log 2>&1 &
until grep -qE 'https://[a-z0-9-]+\.fxtun\.ru' tunnel.log; do sleep 1; done
PUBLIC_URL=$(grep -oE 'https://[a-z0-9-]+\.fxtun\.ru' tunnel.log | head -n 1)
echo "$PUBLIC_URL"
```

Цикл `until` ждёт строку `HTTPS:` с адресом. Если клиент не подключится, строки не будет; в рабочем пайплайне добавьте к циклу ограничение по времени. Через 30 минут туннель закроется, клиент напишет `All tunnels closed, exiting` и завершится сам.

На бесплатном тарифе туннель один, и каждый запуск получает новый случайный поддомен. Для пайплайнов с несколькими туннелями нужен тариф Base.

## Какой срок выбрать

Готовых правил нет, но от задачи отталкиваться проще, чем от чисел:

| Задача | `--auto-close` | `--max-lifetime` |
|---|---|---|
| Показать страницу коллеге | `20m` | `2h` |
| Демо заказчику на встрече | `1h` | до конца рабочего дня, например `10h` |
| Приём вебхуков во время отладки | не ставить: события приходят редко | `8h` |
| Доступ к RDP или SSH | `15m` | `1h` |
| Туннель в CI | не нужен | чуть дольше самой задачи |

С вебхуками `--auto-close` мешает. Сервис может молчать час, а туннель за это время закроется, и следующее событие уйдёт в пустоту. Здесь хватит одного `--max-lifetime`.

С RDP наоборот: пока коллега работает в сессии, по ней идут данные, и туннель живёт. Коллега отключился, данные перестали идти, и через 15 минут туннель закрывается сам, даже если час ещё не прошёл.

## В конфигурационном файле

Флагам соответствуют поля `auto_close` и `max_lifetime` у каждого туннеля ([документация](https://fxtun.ru/docs/config)):

```yaml
# fxtunnel.yaml
tunnels:
  - name: demo
    type: http
    local_port: 3000
    basic_auth: "client:DemoPass-2026x"
    auto_close: 1h
    max_lifetime: 10h
```

Запуск:

```bash
fxtunnel --config fxtunnel.yaml
```

Значения проверяются при чтении файла, по тем же пределам. Ошибка укажет номер туннеля в списке, считая с нуля: `Error: validate config: tunnel[0]: auto-close maximum is 24h, got 48h`.

Если в фоне уже работает `fxtunnel up`, команда `fxtunnel http 3000 --max-lifetime 2h` не запустит отдельный клиент. Она передаст туннель фоновому процессу, напечатает `Tunnel added: …` и вернёт управление. Таймер тогда считает фоновый процесс, а обёртка `timeout` над такой командой ничего не ограничивает.

## Чего таймеры не делают

- **Не заменяют защиту.** Пока туннель открыт, адрес публичный. Пароль (`--auth`, только HTTP) и список адресов (`--allow-ip`, HTTP, TCP и UDP) нужны и временному туннелю.
- **Не гарантируют жёсткий предел при обрывах.** После переподключения отсчёт начинается заново. Для строгого предела ограничьте время жизни процесса системой.
- **Не открывают туннель снова.** Закрытый по таймеру туннель не вернётся ни при переподключении, ни сам по себе. Понадобился снова? Запустите команду ещё раз. Адрес при этом будет новым, если не задан `--domain` для HTTP или `--remote-port` для TCP и UDP.
